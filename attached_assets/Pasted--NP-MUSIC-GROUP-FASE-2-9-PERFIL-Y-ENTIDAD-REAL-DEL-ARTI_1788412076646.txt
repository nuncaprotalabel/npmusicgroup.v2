# NP MUSIC GROUP — FASE 2.9: PERFIL Y ENTIDAD REAL DEL ARTISTA

## OBJETIVO

Construir la estructura real de artistas de NP Music Group y conectar cada cuenta `ARTIST` con su artista correspondiente.

Actualmente ya funciona:

**Solicitud → Invitación → Contrato → Firma → Onboarding → Cuenta ARTIST → Activación → Login**

La Fase 2.8 terminó con el artista pudiendo iniciar sesión.

Ahora debemos convertir esa cuenta en un **artista real dentro del sistema**.

El objetivo de esta fase es dejar funcionando:

**USER ARTIST → ARTIST → PERFIL DEL ARTISTA**

Esta entidad será la base futura para:

* catálogo
* releases
* distribución
* ingresos
* estadísticas
* colaboradores
* contratos
* operaciones del artista

NO implementar todavía esas funciones.

---

# 1. ENTIDAD ARTIST

Si después de inspeccionar el schema se confirma que todavía no existe una entidad equivalente a `artists`, crearla siguiendo la arquitectura existente.

Si ya existe una estructura equivalente:

**REUTILIZARLA.**

La entidad `artist` representa al artista como entidad de negocio.

No debe confundirse con:

* `users` → cuenta/autenticación
* `solicitudes` → solicitud original
* `artist_onboarding` → proceso de incorporación
* `contracts` → relación contractual

La relación conceptual debe ser:

```text
USER
 ↓
ARTIST
```

Y el artista debe poder relacionarse con:

```text
SOLICITUD
CONTRATO
```

utilizando las relaciones existentes cuando sea apropiado.

---

# 2. RELACIÓN USER ↔ ARTIST

Cada artista debe estar asociado a una cuenta `users`.

Regla:

**Un usuario con rol ARTIST debe corresponder a un único artista.**

Evitar:

* dos artistas para el mismo usuario
* dos usuarios para el mismo artista
* relaciones duplicadas

La relación debe estar protegida mediante una restricción/índice adecuado.

NO modificar automáticamente cuentas que tengan otro rol.

---

# 3. CREACIÓN DEL ARTISTA

El artista debe crearse como parte del flujo real de onboarding.

Utilizar la información ya existente en:

* `users`
* `solicitudes`
* `artist_onboarding`
* `contracts`

No pedir nuevamente al artista información que ya tenemos almacenada, salvo que sea información adicional realmente necesaria.

El proceso debe ser idempotente.

Si el artista ya existe:

**NO crear otro.**

---

# 4. INFORMACIÓN DEL PERFIL

El perfil inicial debe aprovechar la información que ya fue proporcionada en `/aplicar`.

Como mínimo debe poder representar:

* nombre artístico
* email
* país
* género principal
* enlace principal
* Instagram
* TikTok
* presentación/bio

No duplicar innecesariamente el email de `users` si la arquitectura puede obtenerlo mediante la relación.

El nombre artístico debe ser tratado como información del artista, no como username de autenticación.

---

# 5. IDENTIDAD DEL ARTISTA

Debe quedar claramente separado:

### USER

Responsable de:

* login
* contraseña
* sesión
* rol
* permisos
* estado de cuenta

### ARTIST

Responsable de:

* identidad artística
* perfil
* información pública/profesional
* futuras relaciones con música, releases, catálogo e ingresos

Esto es importante porque posteriormente un artista puede tener muchas entidades relacionadas con él.

La arquitectura futura debe poder representar:

```text
ARTIST
 ├── RELEASES
 ├── TRACKS
 ├── CATALOG
 ├── DISTRIBUTION
 ├── INCOME
 ├── COLLABORATORS
 └── CONTRACTS
```

NO implementar esas tablas todavía.

---

# 6. ESTADO DEL ARTISTA

Utilizar únicamente los estados que realmente sean necesarios.

Como mínimo debe poder distinguirse entre:

* onboarding pendiente
* activo

Si el sistema existente ya tiene estados adecuados para este propósito, reutilizarlos.

NO crear una cantidad innecesaria de estados.

Importante:

El estado del artista NO debe reemplazar el estado de la cuenta `users`.

Son conceptos diferentes:

```text
USER → activo/inactivo
ARTIST → estado dentro del ecosistema
```

---

# 7. PERFIL DEL ARTISTA

Crear dentro del dashboard ARTIST una sección para consultar su perfil.

Ruta sugerida:

```text
/dashboard/perfil
```

Si el proyecto ya tiene una convención equivalente para el perfil, reutilizarla.

El artista debe poder:

* ver su información
* editar los campos permitidos
* guardar cambios

El artista únicamente puede modificar **su propio perfil**.

No confiar en un `artist_id` enviado desde el frontend.

El servidor debe obtener el artista asociado a la sesión autenticada.

# 15. VERIFICACIÓN

Probar como mínimo:

### Caso correcto

1. Utilizar una cuenta ARTIST real existente.
2. Confirmar que existe su artista correspondiente.
3. Entrar al dashboard.
4. Abrir perfil.
5. Consultar información.
6. Modificar información permitida.
7. Guardar.
8. Recargar.
9. Confirmar persistencia en Neon.

### Seguridad

Confirmar que un ARTIST:

* no puede editar otro artista
* no puede cambiar su rol
* no puede cambiar permisos
* no puede modificar contratos
* no puede acceder a administración

### Integridad

Confirmar:

* no existen artistas duplicados
* un usuario ARTIST no tiene múltiples artistas
* la relación con solicitud/onboarding no genera duplicados
* los cambios permanecen después de cerrar sesión

Ejecutar:

```text
npx tsc --noEmit
npm run build
git diff --check
```

Si existen pruebas relevantes, ejecutarlas.
