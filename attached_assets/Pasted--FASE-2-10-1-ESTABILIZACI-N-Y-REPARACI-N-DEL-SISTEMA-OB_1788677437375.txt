# FASE 2.10.1 — ESTABILIZACIÓN Y REPARACIÓN DEL SISTEMA

## OBJETIVO

DETENER temporalmente el desarrollo de nuevas funcionalidades.

El objetivo de esta fase es hacer que el sistema existente sea realmente funcional, estable y conectado a Neon PostgreSQL.

NO implementar Releases nuevos, distribución, royalties ni nuevas funcionalidades de negocio.

---

# PRIORIDAD ABSOLUTA

Existen problemas actuales:

1. El panel administrativo tiene botones y navegación que no funcionan correctamente.
2. Algunas funciones funcionan y después dejan de funcionar.
3. El menú lateral/móvil de tres rayas presenta problemas.
4. Existen botones de la web pública que no hacen nada.
5. Algunas secciones no están correctamente conectadas con datos reales.
6. El selector de idioma del área privada no traduce toda la interfaz.
7. La web se siente poco optimizada.

REPARA ESTOS PROBLEMAS ANTES DE CONTINUAR EL DESARROLLO.

---

# REGLA DE TRABAJO

NO rehagas la arquitectura.

NO reemplaces autenticación.

NO reemplaces RBAC.

NO reemplaces Neon/PostgreSQL.

NO reemplaces contratos.

NO reemplaces onboarding.

NO reemplaces artistas.

NO reemplaces releases.

NO instales dependencias innecesarias.

NO hagas un refactor general.

Primero identifica la causa concreta del problema y después modifica solamente los archivos necesarios.

* scroll
* botones internos

* cambiar idioma

* Inicio

* Blog

* footer

Regla:

**Si existe visualmente, debe funcionar.**

Eliminar cualquier:

* `href="#"`

* estadísticas inventadas

mostrar un estado vacío profesional.

---

# 5. CONSISTENCIA ENTRE FRONTEND Y API

Para cada módulo existente verifica:

**UI → API → servicio/query → Neon**

Si un botón existe pero no tiene endpoint:
→ determinar si la acción debería existir según la funcionalidad actual.

Si la API existe pero falla:
→ corregirla.

Si el frontend llama a una ruta incorrecta:
→ corregir la llamada.

Si existe una ruta antigua y otra nueva:
→ mantener una única ruta funcional y redirigir correctamente cuando corresponda.

NO crear APIs duplicadas.
