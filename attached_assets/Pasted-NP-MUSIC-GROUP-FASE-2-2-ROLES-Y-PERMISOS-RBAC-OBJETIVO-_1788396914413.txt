==================================================
ROLES DEFINITIVOS
==================================================

Implementar exactamente estos roles:

SUPER_ADMIN
ADMIN
DISTRIBUTION_MANAGER
MANAGER
ARTIST
VIEWER

No crear otros roles.

==================================================
JERARQUÍA
==================================================

SUPER_ADMIN:

Control absoluto.

Debe poder acceder a todas las áreas administrativas y tener capacidad futura para administrar cuentas, roles, permisos y configuración.

IMPORTANTE:

No implementar todavía esas funciones.
Solo dejar la autorización preparada.

ADMIN:

Acceso administrativo general, pero siempre por debajo de SUPER_ADMIN.

DISTRIBUTION_MANAGER:

Acceso relacionado con lanzamientos y distribución.

MANAGER:

Acceso relacionado con artistas y gestión.

ARTIST:

Acceso únicamente a las áreas propias del artista.

VIEWER:

Acceso estrictamente de lectura donde corresponda.

==================================================
AUTORIZACIÓN REAL
==================================================

Los permisos deben verificarse SERVER-SIDE.

Nunca confiar únicamente en:

- botones ocultos
- componentes React
- rutas del frontend
- JavaScript del navegador

Un usuario no autorizado no debe poder ejecutar directamente un endpoint/API protegido aunque intente acceder manualmente a la URL.

Crear una capa reutilizable de autorización, por ejemplo:

requireRole(...)
requirePermission(...)

o una estructura equivalente coherente con la arquitectura existente.

NO crear una arquitectura innecesariamente compleja.

IMPORTANTE:

No crear todavía funcionalidades nuevas dentro de /admin.

Únicamente preparar el acceso según rol/permisos.

==================================================
VERIFICACIÓN
==================================================

Al terminar comprobar:

1. SUPER_ADMIN puede autenticarse.
2. SUPER_ADMIN conserva acceso a /np-control.
3. Usuarios sin autenticación no pueden acceder a áreas protegidas.
4. Un usuario con un rol sin permiso no puede ejecutar directamente un endpoint protegido.
5. La autorización funciona server-side.
6. Los roles existen correctamente en Neon.
7. Los permisos existen correctamente en Neon.
8. Las relaciones rol-permiso son correctas.
9. No existen contraseñas o secretos en el código.
10. Build correcto.
11. TypeScript correcto.
12. / continúa funcionando.
13. /aplicar continúa funcionando.
14. Login/logout continúan funcionando.

Si no existe una forma segura de probar otros roles porque todavía no tenemos cuentas de esos tipos, NO inventes usuarios para hacerlo.
